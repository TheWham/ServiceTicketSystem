# IT 服务台前端设计方案

日期：2026-10-08。状态：用户已确认方案 A，已按本方案实施现有业务页面的前端改造。实现与验证边界见同目录 `2026-10-08-service-desk-ui-validation.md`。

## 依据与目标

- 用户提供的 `C:/Users/admin/Desktop/原型图` 共 15 张 JPG。
- 当前 `frontend` 使用 Vue 3、Vite、Pinia、Vue Router、Element Plus。
- 业务依据为 `docs/IT服务工单系统PRD-Ultimate.md`，现有代码及接口作为接入依据。
- 已查看全部原型页面、路由、应用布局、页面组件和 API 客户端。工作区有未提交的咨询接入等改动，实施时基于这些改动增量调整。
- 目标：统一视觉、完善原型的信息层级与交互，让员工快速求助，让工程师清楚下一步，让管理员发现异常。

设计预览：同目录 `2026-10-08-service-desk-ui-preview.svg`。图中的姓名、工单和会话均为设计示例。

## 方案比较

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| A. 企业服务工作台（推荐） | 深蓝侧栏、浅色内容区；适合多角色、长时间使用；沿用当前布局 | 需要重整导航与页面层级 |
| B. 原型精修 | 保留顶部蓝色导航；与截图最接近 | 功能增加后顶栏拥挤，小屏适配复杂 |
| C. 对话优先门户 | AI 咨询视觉集中、员工上手快 | 工程师与管理端需要另一种布局，整体一致性较弱 |

选择 A；员工端突出求助入口，工程师端突出待办，管理端突出异常。所有角色使用相同布局和组件规范。

## 技能检索与取舍

使用 `ui-ux-pro-max`：

1. `IT service management dashboard --design-system`：结果偏向运维大屏，OLED 黑底和衬线字体不符合中文办公界面，未采用、未保存原始结果。
2. 缩窄为 `enterprise SaaS dashboard minimal --design-system`：蓝色主色、浅色背景、企业无衬线字体符合本项目；其中营销落地页结构及大面积玻璃效果不适用，未采用。
3. Vue 搜索 `form feedback accessibility` 无结果，按技能要求重试 `forms`，得到表单校验和 v-model 建议。保留项目现有 Element Plus 表单校验，无需引入第二套表单库。

下述颜色与层级是结合检索结果、原型和中文桌面场景的人工设计，不代表完整套用数据库输出。

## 页面设计与原型对应

| 原型 | 完善后的设计 | 接入边界 |
| --- | --- | --- |
| 1 登录 | 左侧品牌与服务流程，右侧账号密码表单；可见标签、错误信息、忘记密码、提交反馈 | 保留真实认证，角色由登录结果决定 |
| 2.1 发起咨询 | 左侧服务导航，中间会话，右侧当前咨询信息；欢迎态提供可编辑的问题建议；输入区始终可达 | 复用 ConsultationChat，保留引用、拒答、反馈、转人工和直接提单 |
| 2.2 提交工单 | 问题信息、位置资产、附件三个分区；右侧说明；显示草稿与咨询来源 | 复用草稿、附件、建单接口；员工确认后提交 |
| 2.3 我的工单 | 状态筛选、搜索、待我处理提示、列表；标题优先，次要字段折叠 | 统计必须对应真实范围；不能将当前页数量写成总量 |
| 2.4 工单详情 | 标题与状态摘要、时间线、解决方案；右侧处理人及 SLA；底部显示当前可执行操作 | 复用真实九态工单状态机，完成后评价；通知深链接仍可打开详情 |
| 3.1 工单池 | 待领取视图，优先级和 SLA 同列层级突出；接单时确认影响范围与紧急程度 | 复用 claim，不改变分配权限 |
| 3.2 我的任务 | 我的任务列表进入详情；处理进度、补充材料、外部等待与提交方案分组 | 状态操作按后端许可显示；错误保留输入 |
| 3.3 已完成 | 按时间与关键词检索；显示结果、耗时和评价；知识状态有数据时才展示 | 已完成与已关闭使用不同文字，不能混用 |
| 4.1 会话队列 | 工程师的人工咨询工作区：会话列表、当前对话、上下文信息 | 当前 PRD 不设坐台客服，复用 EngineerConsultation 与 consultationApi |
| 4.2 处理工作台 | 在当前人工咨询中显示问题信息与解决结论；持续保留聊天上下文 | 不直接启用未接入路由的旧 AgentWorkbenchView |
| 4.3 提单卡片 | 会话内显示提交工单入口，员工进入可修改的预填表单 | 工程师发送入口，员工最终提交；不静默代提交 |
| 5.1 数据看板 | 当前可实现的工单概览与异常处理；原型趋势图定义为后续运营扩展 | 前端 API 客户端未发现完整运营聚合接口；原型 68%、96.2% 等均不作生产数据 |
| 5.2 团队监控 | 管理工单表、处理人筛选、改派入口；负载与绩效扩展另列 | 沿用平台管理员权限；完整负载统计需服务端数据支持 |
| 5.3 知识库管理 | 文档导入、处理记录、待审核、已发布和已下线；详情展示版本与审核操作 | 由知识库管理员操作，沿用 ragApi 生命周期接口 |
| 5.4 流程配置 | 设计中保留规则分组方案；已验证可读取的规则可作只读展示 | 当前缺少配置 CRUD 客户端，不渲染可假保存的编辑表单 |

原型“人工客服/管理人员”按最新业务规范映射为工程师、平台管理员及知识库管理员的权限包，不增加独立客服或主管角色。

## 导航与交互

- 员工：智能客服、提交工单、我的工单。默认首页沿用当前业务规则，侧栏明确标出当前位置。
- 工程师：工单池、我的任务、已完成、人工咨询；可使用现有页内视图，并将视图状态与 URL 同步。
- 平台管理员：工单概览、工单管理、账号管理。未接入的运营统计与流程配置仅出现在设计说明中。
- 知识库管理员：文档导入、知识管理。兼容 KNOWLEDGE_ADMIN 与已有 KB_ADMIN 别名，菜单与路由权限一致。
- 工单详情属于具体工单，不作为没有上下文的固定一级导航；列表、通知与深链接均可打开。
- 列表刷新保留筛选与页码；切换筛选回第一页；空数据与加载失败采用不同反馈，失败提供重试。
- 提交过程中禁用重复操作；错误保持用户输入；成功后展示真实工单号并提供查看入口。
- AI 输入支持中文输入法，不在候选确认时发送；快捷问题先填入编辑框；AI 不可用时保留人工与提单入口。
- 对话滚动：用户停留在历史消息时不强行跳到底部，出现新消息提示；输入与会话状态保持可见。
- 所有流程提示面向业务用户，隐藏不帮助决策的实现术语；知识管理中按需保留技术处理详情。

## 响应式与可访问性

- ≥1200 px：完整侧栏；聊天和详情支持主辅两栏。
- 768–1199 px：紧凑侧栏，辅助信息折叠到独立区块。
- <768 px：抽屉导航，表单单列，详情全屏；列表保留标题、状态、主要操作，次要信息收起。复杂管理表格允许容器内部滚动，页面本身不横向溢出。
- 图标按钮具备可访问名称；状态由颜色、文字共同表达；键盘焦点可见；弹窗关闭后焦点返回触发入口。
- 错误展示在相关字段附近；提交失败定位首个错误；输入框具有真实标签。
- 动效采用短淡入和颜色过渡，支持 prefers-reduced-motion；不添加持续闪烁装饰。
- 验证 375、768、1024、1440 px，以及明暗主题和键盘操作。

## 实施架构与顺序

这是一次统一前端改造，按共享基础及角色页面分批实施，避免扩展为后端业务重建：

1. 提取语义样式变量与少量共享组件（页面标题、状态说明、空态），升级 App 布局与登录。
2. 员工端：咨询、提单、列表、详情，保留正在进行的咨询接入成果。
3. 工程师端：任务视图、详情与人工咨询统一视觉。
4. 管理端：现有工单、账号、知识生命周期页面统一；新统计及配置功能按上表边界处理。
5. 检查响应式、主题、关键交互和构建，交付实际页面截图与已知限制。

组件只接收展示数据和发出用户操作事件；API 请求继续通过现有客户端，咨询与工单各自保留返回包络处理和幂等逻辑。路由守卫继续负责访问限制，菜单仅作展示。先复用现有组件，再按明确重复点提取共享组件，不进行无关重构。

## 验收标准

1. 导航能到达对应现有业务页面，刷新与通知详情入口可用，权限不扩张。
2. 登录、咨询发送/失败恢复/转人工/预填提单、工单筛选/详情、工程师操作、知识审核功能无视觉改造引起的回归。
3. 所有修改页有一致的标题、主操作、状态、空态和失败反馈。
4. 真实指标与演示数据明确区分；不使用原型数字冒充生产统计。
5. `npm run build` 成功；现有 `node --test tests/*.test.mjs` 先记录基线，再比较改造后的结果；仅对新增路由或行为变化补充有意义的测试。
6. 浏览器检查关键页面、明暗主题、四档屏宽与键盘操作；若服务不可用，明确区分接口桩验证和真实联调结果。
