### 【02:00 - 05:00】第一篇章（Day 11~15）：垂直知识库 RAG 核心技术攻坚与指标量化

*(点击 PPT 切换至：RAG 检索流水线与评测雷达图)*

我们的第一场硬仗，是构建**高精度、防扯皮的企业垂直知识库**。

很多初学者以为，RAG 就是把 PDF 扔进向量数据库，然后发给模型。但在真实 IT 运维中，这种做法直接导致回答灾难。在 Day 11 到 Day 12，我负责对全公司 38 篇 IT 核心规章进行非结构化治理。我们发现，业界通用的按字数固定切块，会生生切断操作步骤的上下文。为此，我规范设计并实现了**基于 Markdown 标题树层级的结构化分块管道**，并全链路接入 1024 维语义向量模型，使向量空间的聚类区分度提升了 32%。

*(语速稍缓，加重专业技术词汇)*

紧接着在 Day 13，我们遇到了一个经典难题：用户报修经常包含冷僻代码，比如“错误码 0x0000007B”或“驱动 nvlddmkm.sys 崩溃”。纯向量模型对这种专有名词极其迟钝，频繁漏召回。

为此，我设计并落地了 **“1024 维向量语义 + BM25 关键词”的双路召回引擎**。一方面靠向量召回语义意图，另一方面靠 BM25 锁死代码关键字；然后通过 **RRF（倒数排名融合算法）** 进行加权互补，并在最上层引入 **Cross-Encoder 深度重排模型（Rerank）**。重排模型逐字比对问题与候选块的相关性，彻底排除了“字面相似但逻辑无关”的脏片段，使 Top-3 召回精准度大幅跨越！

*(展示黄金测试集跑测报告)*

检索准了，模型会不会根据过时规章瞎编？在 Day 14，我主导建立了 **6:2:2 工业级黄金测试集**。我们专门设计了大量版本冲突题（比如用去年的旧报销标准设套）和恶意边界陷阱。

在 Day 15 的全量自动化回归跑测中，我们用实测数据证明了质量：
- 越界与废止条款拦截率达到 **100%**；
- 答案参考来源角标溯源率达到 **100%**；
- 单次检索平均耗时仅为 **11.7 毫秒**。

这套垂直 RAG 内核，为后续智能体的每一次推理提供了绝对真实、不可篡改的事实源底座！

### 【05:00 - 08:30】第二篇章（Day 16~20）：安全 AST 拦截、确定性编排与三位一体 Agent

*(点击 PPT 切换至：安全 AST 语法树与 HITL 人机回环流程)*

知识库就绪后，从 Day 16 开始，我全面推进 Agent 智能化闭环：**让 AI 具备业务执行力，但必须戴着铁链跳舞！**

大模型具备调用工具（Function Calling）的能力，但如果放任它自由拼接 SQL 读写数据库，系统将面临灾难级的越权风险。

在 Day 16 到 Day 17，我主导攻坚了 **安全 Text2SQL 架构与 AST 抽象语法树拦截器**。大模型生成的任何 SQL 在执行前，绝不直接交给驱动执行，而是被强制送入 Python 抽象语法树进行深度语法解析。我们的分析器仅开放只读 `SELECT` 语法节点白名单并限定查询边界，只要检测到 UPDATE、DELETE、DROP、ALTER 等写操作，哪怕攻击者使用了注释混淆或 SQL 注入绕过手段，也会在应用解析层被**物理阻断、瞬间击毙，100% 杜绝数据库被恶意篡改**！

到了 Day 18，我将业务推进到了核心关键点：**“知识库 + 数据库 + 外部 API”三位一体协同架构**。

在企业里，如果大模型直接帮员工代转派工单或审批报销，出了事故责任谁担？为了解决合规与归责痛点，我首次落地了 **HITL（人机协同）断点机制**。大模型无权直接写库，当它识别到用户想要转派工单时，系统会生成一份带有风险标记的《派单草案》，并在前端界面冻结流转、弹出确认卡片。必须由主管或工程师人工核验并点击“批准”后，状态机才会被唤醒并真正落库！

在 Day 19~20 的第二阶段验收中，我们还通过混沌工程模拟了向量库宕机与接口超时，系统凭借完备的 Fallback 降级策略优雅兜底，平稳通过了 Demo Day 质量大盘考核！

### 【08:30 - 12:30】第三篇章（Day 21~29）：高阶 GraphRAG、LangGraph、MCP 与多 Agent 生产发布

*(点击 PPT 切换至：GraphRAG 拓扑因果推理演示，进入全场高潮)*

如果说前两周是在筑牢防线，那么最后这 9 天（Day 21 到 Day 29），则是我在技术突破最大、也最具工业实用价值的阶段。我主导攻克了五大关键技术：

**第一项突破，是攻克多跳因果推导，落地 GraphRAG（Day 21~22）。**  
在现实 IT 运维中，很多问题存在复杂的因果级联：比如用户反馈“远程桌面连不上”，文档 A 写着“远程服务依赖域控 DNS”，文档 B 写着“域控 DNS 依赖主板时钟”。这种跨文档的隐性关联，纯向量相似度检索 100% 会失败！  
为此，我主导将核心知识沉淀为实体三元组入驻 **Neo4j 图数据库**，结合自适应意图路由执行 2-Hop 多跳拓扑推理；同时动态生成因果推导拓扑链条，用户点击提问，系统即刻动态绘制出白盒因果链路，让 AI 的逻辑真正“看得见、摸得着、可溯源”。

**第二项突破，是编排框架全面演进为 LangGraph 原生状态图（Day 23~26）。**  
传统的无状态 ReAct 循环极易陷入死循环，且一旦进程中断上下文全丢。我重构了基于 LangGraph 的编排中枢，并引入了 **持久化 Checkpointer 快照机制**。  
在重大审批节点，系统触发原生 `interrupt()` 挂起。我们现场做过极其残酷的断电模拟测试：在审批挂起时直接强杀后端服务，重新开机后，只要传入 Session ID，系统能从快照数据库秒级还原上下文并无缝唤醒，实现了真正的**状态零丢失、生产级高可用**！

**第三项突破，是落地 Anthropic FastMCP 工业标准互联协议（Day 27）。**  
我基于原生 Python 实现了轻量级 FastMCP 规范，将工单中心与 HR 组织架构封装为标准 MCP 工具端点，完成了 MCP Client 与 OpenAI 工具适配器的双向握手，使底层工具具备了与各类主流客户端即插即用的解耦扩展能力。

**第四项突破，是落地 Supervisor-Worker 多智能体架构与 Guardrails 双向护栏（Day 28）。**  
由 Supervisor 调度主控负责动态意图分发，指挥知识专家与工单专家两个独立子图协作。在入口端，部署并调优了 **Guardrails 安全引擎**，在请求进入模型前以 0 Token 消耗秒级拦截恶意越狱攻击；在出口端，对手机号、身份证号、银行卡执行自动正则脱敏掩码，守死数据合规红线！

**第五项突破，是生产级性能治理与高并发发布（Day 29）。**  
很多领导都关心：“调一次大模型要好几秒，每天成千上万次调用，公司的 API 账单会不会被刷爆？”为了解决性能与成本的矛盾，我上线了两大降本与性能引擎：
1. **Model Router 动态阶梯选模**：精准识别用户意图复杂度，复杂多跳推导走高阶模型，日常高频事实查验路由给极速轻量模型，杜绝大材小用，全链路综合 Token 账单直接下降超过 **42.3%**；
2. **FastAPI SSE 高并发流式引擎**：基于异步事件循环（Asyncio）构建打字机流式推送，首字等待时间（TTFT）压降到 380 毫秒以内，同时动态广播 Agent 思考过程，让前端交互极致平滑丝滑。

至此，一个兼具高推理能力、严苛安全防线与极低运营成本的工业级智能体中枢全面总装就绪！

## 💡 随身备忘：现场答辩“高频四问”必杀防守卡

在答辩 Q&A 环节，若专家提问，请立刻调取以下精准防御话术：

1. **问：“为什么既有向量检索，还要上 BM25 和 Rerank？”**
   - **答**：“纯向量在处理专有 IT 代码（如报错代号 `0x0000007B`、指令 `regedit`）时存在稀疏词表征盲区；BM25 擅长字面硬匹配。我们用 RRF 融合互补，再由 Cross-Encoder 深度打分，排除语义无关项，这是工业级生产 RAG 的必备标准。”
2. **问：“Neo4j 图谱到底比大块召回强在哪里？”**
   - **答**：“大块召回解决的是单点段落的完整性；而 Neo4j 解决的是跨文档‘隐性因果推导’。如‘VPN 连不上’表面看似网络问题，因果链下游却是‘域控 DNS 欠费’。只有图谱能沿着 2-Hop 实体链条把因果拓扑抽出来，文本召回在原理上做不到。”
3. **问：“服务在审批挂起时突然被运维重启断电，状态怎么找回？”**
   - **答**：“我们在 LangGraph 底层配置了持久化 Checkpointer。每次状态流转或触发中断，全量 State 都会打上单调递增版本号持久化落库。重启后只需传入原 Session ID，系统自动反序列化唤醒快照，等待人工输入，实现真正的零数据丢失。”
4. **问：“综合降本 42.3%、首字响应低于 380ms 怎么做到的？”**
   - **答**：“在实际生产中，不同用户的查询复杂度差异极大。如果所有问题都无脑调用顶级大模型，API 账单会成倍飙升。我们通过 Model Router 意图分流引擎，将简单的规章查询与事实问答路由给轻量极速模型，仅对复杂因果推导启用高阶模型，大幅削减无效 Token 消耗，直接降本 42.3%；同时配合 FastAPI 异步事件流式推送，将首字打字机延迟（TTFT）压降到 380ms 以内。”
