> 一句话分工：**Java 管门禁和账本，Python 管脑和手。**

## 二、三个问题的实测对照（逐层，带函数）

### Q1「VPN连接不上怎么办」— 知识够，走知识库路径

| 层 | 大白话 | 走的函数 | 实测结果 |
|---|---|---|---|
| ⑥ | 看问题里有没有「工单」 | `ToolIntentDetector.matches()` | false（没有那 4 个词）——等于没有这张通行证 |
| ③d 检索 | 去知识库翻资料 | `RagServiceKnowledgeRetriever.retrieve()` → Python `hybrid_rerank_search()` | `domain=OFFICE_IT, reliable=True, items=3, topScore=0.7333` ← **命中了** |
| ③d 筛材料 | 把最高分的切片留下当参考资料 | `RetrievalPolicy.material()` | material 非空（3 条里选出最高分的） |
| ③e 放行 | 要不要拒答 | `ComposedRagAdapter.answer()` | 不需要（本来就没到拒答那一步） |
| ④ 工具 | 模型自己决定要不要查 | `ModelClient.complete_with_tools()` → `dispatch()` → `_search_knowledge()` | 调了 **2 次**，检索词是模型自己拟的 |
| 产出 | 出答案 | `_to_response()` → `AiAnswerGuard.evaluate()` | `ANSWER` + 1 条引用《VPN连接失败》+ conf 0.85 |

工具轨迹（这次新加的日志抓到的）：

```
[工具] 调用 search_knowledge requestId=xxxx 参数={"query": "VPN连接不上 无法连接"}
[工具] 调用 search_knowledge requestId=xxxx 参数={"query": "VPN 认证失败 排查"}
```

**看点**：知识本来就够（material 非空），但模型还是主动补搜了两次——检索词是它自己拟的，不是关键词匹配出来的。这两次调用发生在 `AgentRunner.run()` 的循环里，`dispatch()` 每次都会打一行日志，同一个 `requestId` 把它们串成一条链。

## 三、差异点 A / B 到底是什么

三个问题走了同一条代码路径，差异只在两处，别的地方一模一样：

| | 差异点 | 大白话 | 在哪个函数里被决定 | 后果 |
|---|---|---|---|---|
| **A** | 检索有没有命中 | 资料架上有书还是空的 | `RagServiceKnowledgeRetriever.retrieve()` 拿回 `reliable` → `RetrievalPolicy.material()` 决定留不留 | 决定发给模型的 `material` 是空还是有内容 → 决定模型答的时候「有没有依据」 |
| **B** | 模型选了哪个工具 | 模型伸手拿的是哪件工具 | `ModelClient.complete_with_tools()` 返回的 `tool_calls` → `dispatch()` 按名派发 | 决定答案里的数据从哪来：知识库？工单表？还是只产一张草稿 |

补充一句：**③e 的放行不是第三个差异，它是让 A 为空时还能走到 B 的那个前提。** 没有它，A 为空 = 直接拒答，B 根本没机会发生。

## 四、这次值得讲给非技术同事听的三个设计（附函数级证据）

### ① 模型不决定「发生什么」，只决定「调哪个工具」

`tool_specs()`（[tools.py:47](services/python-retrieval/agent_service/tools.py:47)）里只有一段段自然语言的 `description`——没有任何关键词匹配、没有一行 if-else。模型是**读描述自己判断**的。

至于调完之后数据怎么流转、工单状态怎么变——**全由代码定**：

```python
_HANDLERS = {                        # tools.py:210 —— 允许调用的就这三个，白名单写在代码里
    "search_knowledge": _search_knowledge,
    "query_my_tickets": _query_my_tickets,
    "prepare_ticket": _prepare_ticket,
}
```

模型的名字只要不在这张表里，`dispatch()` 第 108 行直接返回「未知工具」，连试都不会试。

### ② 建单草稿走带外字段，完全不经过模型输出

```python
_prepare_ticket() → ctx.capture_draft(draft)          # tools.py:201  塞进上下文
                 → _to_response(payload, ctx.draft)   # agent.py:111  响应的 ticketDraft 字段
                 → sixKeys(data)                      # 只取 6 个键，草稿被排除在外
                 → draftOf(data.path("ticketDraft"))  # PythonAgentClient.java:78
```

草稿**不走模型那份 JSON**——`sixKeys()` 只抄 6 个字段，`ticketDraft` 从头到尾不在里面。所以模型完全没法自己「建单」：它连草稿该怎么传都不知道，只负责调个工具。

真正建单要等员工在前端点确认，走的是另一条完全独立的链路：`consultation.js:147` → `confirmTicketDraft()` → `TicketServiceClient` → 工单服务。**这就是「AI 按不了那个按钮」的实现方式。**

### ③ 归属安全：creator_id 只取请求头，模型参数里根本没这个键

```python
params = {"creator_id": ctx.user_id, ...}   # tools.py:177
```

`ctx.user_id` 来自 HTTP 请求头 `X-User-Id`（[agent_service/app.py:64](services/python-retrieval/agent_service/app.py:64)），一路是这么传下来的：

```
浏览器登录态 → authzService.currentUser() → new RagCaller(user.userId(), role)
             → RagQuery.caller() → PythonAgentClient 的 Map.of("X-User-Id", query.caller().userId())
             → agent_service 的 Header(default="", alias="X-User-Id") → ToolContext.user_id
```

模型能传的参数只有 `status` 和 `limit`（[tools.py:74-77](services/python-retrieval/agent_service/tools.py:74)）。**不是靠提示词喊「不许查别人」，是模型的参数里压根没有这个键**——它想说「查 U_EMP99 的工单」都无处可写。

## 五、这次新加的工具日志

之前**完全没有**工具调用日志——今天排查 `search_knowledge` 为什么失败时，因为看不到它到底调没调，绕了远路。现在补在 [tools.py:112](services/python-retrieval/agent_service/tools.py:112)：

两个要点：

- `requestId` 把一轮 ReAct 里的多次调用串起来（多次调用共用一个 requestId，见 `ToolContext.request_id` [:41](services/python-retrieval/agent_service/tools.py:41)）；它优先透传上游 Java 带来的 `X-Request-Id`，缺失才自己生成一个。
- 日志能出来还得感谢 [app.py:26](services/python-retrieval/agent_service/app.py:26) 那一行 `logging.basicConfig(level=logging.INFO, ...)`——uvicorn 只配它自己的 logger，不显式设级别的话，这个服务的 INFO 日志根本不输。

## 六、一页速查：三个问题各自调过哪些工具

| 问题 | `search_knowledge` | `query_my_tickets` | `prepare_ticket` | 发出的外部 HTTP |
|---|---|---|---|---|
| Q1 VPN连不上 | ✅ 调了 2 次（模型自拟检索词） | — | — | consultation 知识搜索 ×2 |
| Q2 查我的工单 | — | ✅ 1 次 `{"limit": 10}` | — | ticket-service `/api/internal/tickets` ×1 |
| Q3 新建工单 | — | — | ✅ 1 次（纯本地） | **0 个** |

> 细心的同事会问：Q1 明明「reliable=True 已经命中了」，为什么模型还自己去补搜？因为备料（`RetrievalPolicy.material()`）和用工具（`dispatch()`）本来就是两条独立的机制——备料是 Java 提前做的，工具是 Python 里模型自己决定的。模型觉得手上材料不够，就会自己去拿，这不冲突。
