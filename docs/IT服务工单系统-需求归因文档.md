## 3. 三维全景透视（AI 相关功能的深度展开）

### 3.1 深度透视：【F-03 高频问题库与相似工单推荐】

**1）检索与数据工程域（输入什么数据与凭证）**

语料来源：已关闭工单的「标题 + 分类 + 问题描述 + 最终解决方案」，必须脱敏（剔除员工姓名、工号、资产编号、内网 IP）；

切分策略：按「问题现象 / 排查步骤 / 解决方案」三段式结构化切分，禁止机械按 500 字定长切分（会切断操作步骤的因果链）；

检索链路：BM25 抓分类关键词 → 向量召回 Top20 → BGE-Reranker 重排取 Top3；

**2）流程与编排工程域（经历什么控制与防线）**

触发时机：`category` 选中后 300ms 防抖触发，异步非阻塞；

超时防线：接口 > 2s 超时立即静默隐藏推荐卡，不弹错误框、不阻塞提单（PRD 已定义，这是本系统最漂亮的一条降级设计）；

未决日志：搜索词与资产号异步入 MQ，作为后续 FAQ 选题的语料来源；

点击行为回流：员工点击条目 → 打开知识库文章 → 若未解决则"一键提单并自动带上推荐卡上下文"。

### 3.2 深度透视：【功能 C 跨工单宏观聚合归纳】（Day21 交付）

**问题定性**：像「请总结本季度全部网络与打印设备工单的共性根因」这类**跨多记录的宏观归纳**，现有 RAG 链路物理上答不了——`retrieval.top_k = 3` + `rerank_granularity = parent` 意味着最多 3 张父卡进生成层，评测也是单卡命中口径；而**工单从不进入知识库**（知识库语料是 35 张 Wiki 卡片，工单在 `ticket` 表）。检索器只会捞回 3 条孤立的单次维修记录，模型基于这 3 条硬凑"三大根因"，是以偏概全的系统性来源。**这不是调参能解决的，是结构缺口。**

**为什么不用 Text2SQL**（P0-1 原计划）：SQL 结构由模型生成则不可控、不可审计、无法单测；且库里存的是**未清洗**原始工单——直接 `GROUP BY` 会把联调测试单算进分母，而 `taxonomy` 词表的症状维度根本无法用 SQL 表达。故改为**确定性聚合**：模型不参与任何数字计算。

**1）检索与数据工程域（输入什么数据与凭证）**

- **取数**：`ticket-service` 新增**只读投影扫描** `GET /api/internal/tickets/analytics/scan`，只按时间窗（`created_after`/`created_before`）过滤，返回脱敏明细（单号/分类/标题/描述/时间列），**不做 `GROUP BY`、不跨库读、不返回姓名与联系方式**（遵守架构 8.1「咨询域不跨库读 ticket 表」）；
- **清洗**：三类噪声在 Python 侧剥离——① `test`/`123`/`[P0-verify]` 等联调噪声；② `prepare_ticket` 生成的「待补充信息」模板话术（模板里的"蓝屏错误代码"举例会污染关键词匹配）；③ 标题自带「请忽略/请勿处理/演示用单」的联调单（内容看着真实，描述里写着可随时撤销）；
- **抽取**：受控词表 `configs/taxonomy.yaml`（症状/设备/根因三类），**最长命中优先**，泛化词必须绑定实体；实测定长匹配会截胡（如 `无反应` 会把「打印机脱机」误判为「无法开机」）；
- **子域过滤**：走 `device`/`symptom` 词典，**不走 `category_id`**——工单分类由提交人手选，实测唯一那张打印机工单的 `category_id` 是 `C_HW_PC` 而非 `C_HW_PR`，按分类过滤会静默丢数据。

**2）流程与编排工程域（经历什么控制与防线）**

- **意图路由**：模型主判 + 规则兜底 + 安全闸（与 `workflow_demo` 的 `route_intent` 同构）；分歧且规则未命中的情形走**澄清**而非直接进链路，因为误判要跨服务边界（普通问答被当成分析题会答非所问）；
- **权限**：跨人聚合是本功能唯一新增权限面，仅 `ENGINEER` / `PLATFORM_ADMIN` 可调，`EMPLOYEE` 直接拒答；三道防线（`AuthzService` / 控制器内 `UserContext` 校验 / Python 侧预检）；
- **小样本闸门**：全库工单数 < 20 整体拒答（说明为何不做归纳）；任意维度条目分母 < 10 或命中 < 5 时**只给计数、不给占比**。用户自己限定子域导致样本少时不拒答——直接推回去没有信息量。

**3）模型生成与推理域（下游怎么消费、怎么防崩坏）**

- **事实包边界**：模型只拿到**已算好的结论**（统计块 + 决策表产出的建议块），**拿不到任何原始工单文本**。占比用 `Decimal` 由代码算并输出**双分母**（以命中工单为分母 / 以全部工单为分母），模型只能引用不能选；
- **数字与单号门禁**：回答里每个百分比/数量必须能在事实包里找到、提到的单号必须在本次样本白名单内，否则该句剔除；剔除后不足则整体退回确定性模板；
- **建议由代码产出**：备件采购与巡检建议由 `ROOT_CAUSE/SYMPTOM → 条目` 决策表映射，**模型只改措辞、无权增删条目**——否则会编造型号、数量与巡检周期；
- **四条降级出口**：无模型 / 模型失败 / 输出不可解析 / 输出被截断，均退回确定性模板文案，且明确区分「没调模型」与「调了但失败」，token 来源分别标注 `estimated` / `reported`。

**4）已知局限（如实登记）**

- **根因维度可用，但当前库里的数据是演示数据**：`ticket_resolution` 已由 `tools/seed_ticket_resolutions.py` 写入 **28 条**处置记录，根因维度因此可归纳（实测：电源故障 6 单 25.0% / 驱动缺陷 6 单 25.0% / 内存故障 5 单 20.8%）。⚠️ **这 28 条是按工单实际症状写的演示数据，不是真实业务沉淀**——主键 `DEMO-RES-` 前缀、可一键回滚。删掉它们，本维度会如实退回「无解决方案记录，不可归纳」而非编造。另需注意：**服务端没有任何代码写这张表**（Java 侧零引用），真实数据得由业务侧先沉淀；
- **服务端不写处置记录**：`ticket_resolution` 在代码里只有级联删除（`TicketPurgeMapper`），没有写入方。分析链路的根因维度依赖它，但**补齐它属于业务侧的事**，不是这条链路的职责；
- **此前该缺口未被文档记录**：宏观聚合类问题一直是当前架构的未文档化能力缺口，本次补齐登记。

## 改造前后职责对照

| 环节                 | 改造前（纯人工）                                             | 改造后（系统自动 + 人工介入）                                |
| :------------------- | :----------------------------------------------------------- | :----------------------------------------------------------- |
| **工单受理与分类**   | 员工在微信/电话里口头报修，IT 同事凭聊天记录与记忆手工登记；信息缺截图、缺设备号，来回追问 | 结构化表单强制带齐分类、描述、截图、资产编号；提交即校验合规性，资产编号自动比对 CMDB；信息不全或 24h 内重复提单自动挂起转人工确认 |
| **优先级与派单**     | 主管凭印象判断紧急程度，逐个打电话/口头联系维修人员；谁有空谁去 | 按优先级、技能标签与实时在手工单负荷自动生成派单草案；主管一键确认（可改派）后生效；无匹配人员或紧急工单自动升级人工调度 |
| **过程跟踪**         | 员工反复打电话问进度，IT 手动翻聊天记录回复；单子走到哪了没人说得清 | 状态变更自动同步提单人（全节点通知）；SLA 超时自动升级提醒主管；员工在列表页自助查进度，无需打扰任何人 |
| **结果反馈**         | 处理完口头说一声；月底凭记忆估算团队工作量，说不清"该不该加人" | 工程师提交方案后自动流转至待验收；员工在线验收评价；满意度、MTTR、分类分布、工程师工作量由系统自动统计成报表 |
| **异常与高危操作**   | 全靠个人经验，无统一防线；漏单、忘单、责任不清无人发现       | 改派/关闭/驳回等写操作强制走状态机白名单校验；全量流转日志可逐单回溯；超时未补充自动挂起或取消，异常流转实时告警主管 |
| **知识沉淀与复用** ★ | 同类问题反复问，经验只存在老员工脑子里，人一走就断档         | 已关闭工单自动脱敏归档为 FAQ；提单时自动推荐相似历史工单与解决方案摘要 |
