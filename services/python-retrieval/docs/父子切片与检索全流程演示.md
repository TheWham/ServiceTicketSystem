## 一、一句话概念

**子块做匹配、父块做上下文。**

- 父块（Parent）：一张 Wiki 卡的正文全文 → 最终交给 LLM 的上下文单元
- 子块（Child）：正文切成 ≤512 字符的片段 → 向量/BM25 的匹配单元
- 纽带：每个子块 metadata 内嵌 `parent_id` + `parent_content`（父块全文）

解决的矛盾：块切小 → 匹配准但上下文残缺；块切大 → 上下文全但向量被稀释。父子切片把**匹配粒度**和**阅读粒度**解耦，两头都要。

## 三、检索全流程：每个阶段做什么、出什么结果

入口：`IndustrialHybridRetriever.hybrid_rerank_search()`（`rag_pipeline/retrieval/hybrid.py:178`），线上由 `rag_service/assembly.py` 装配（演示脚本走的就是同一条路）。

实测查询：**「在家连不上VPN，提示认证失败怎么办」**（逐阶段实测见 `parent_child_retrieval_demo.md`）

### 阶段 A：查询改写（`retrieval/query_rewriter.py`）

- 做什么：LLM 删掉用户对原因的猜测、补规范术语（1.2~2.0s 短超时，失败自动跳过）
- 实测：原查询「在家连不上VPN，提示认证失败怎么办」→ 改写「VPN 连接认证失败，在家无法登录」
- 产出：原查询 + 改写查询 = **四路召回**

### 阶段 B：双路粗排召回（各取 Top-15，全部是子块）

| 通道 | 代码 | 擅长 | 实测 Top-1 |
|---|---|---|---|
| Dense 向量（Chroma 余弦） | `dense_search` [hybrid.py:103](../rag_pipeline/retrieval/hybrid.py) | 意图匹配（"打不开网页"≈"无法访问网站"） | `ITKB-VPN-001#c1` 余弦 0.6622 |
| BM25 关键词（jieba+倒排） | `bm25_search` [hybrid.py:67](../rag_pipeline/retrieval/hybrid.py) | 专有编号/错误码字面命中（IDF 高） | `ITKB-VPN-001#c0` BM25 16.43 |

两路都带元数据硬过滤（默认剔除 `wiki_status=已废止/已下线`）。

### 阶段 C：RRF 倒数排名融合（`rrf_fusion` [hybrid.py:132](../rag_pipeline/retrieval/hybrid.py)）

- 为什么用名次不用分数：BM25 分（0~30+）与余弦分（0~1）量纲不同，直接相加会被大数淹没；名次天然归一。公式 `Σ 1/(60+名次)`，四路同权累加
- 实测：30 个召回（2 查询 × 2 通道）→ 去重融合出 15 个候选子块，`ITKB-VPN-001#c0` 双通道同时靠前，RRF 分 0.03252 登顶

### 阶段 C'：父块去重（精排粒度=parent）

- 多个子块命中同一张卡只留 RRF 分最高的一个
- 实测：15 个候选子块 → **6 张卡**。这就是父子切片的功劳：同一张卡的 4 个子块不会稀释候选位

### 阶段 D：Cross-Encoder 精排（`retrieval/reranker.py`，qwen3-reranker-8b）

- 用整卡全文（parent_content）对改写查询打分，判断"整卡相关性"而非"片段相似"
- 实测：`ITKB-VPN-001` 得 0.8167 分第一；同时演示了**降级路径**——KSP 网关异常时自动回落启发式交叉对齐打分（服务不中断）

### 阶段 E：按秩融合 + 置信度门控 + 保护与拒答

1. **按秩加权**：`0.65/(10+RRF名次) + 0.35/(10+Rerank名次)`——名次化对远程分数漂移免疫，召回侧托底、精排侧提精度
2. **置信度门控**（gate）：按本次打分分布动态定权重。高置信（top1≥0.55 且 margin≥0.10）→ 放权精排 0.35:0.65；低置信/降级 → 召回托底 0.65:0.35。实测因启发式降级走 low 模式
3. **双路共振保护**：父卡同时在 BM25 和 Dense 两侧 Top-2 命中的，保送进最终结果（防精排误杀）
4. **低置信拒答**：最高精排分 < 阈值（远程 0.40 / 启发式 0.25）→ 返回空，宁可拒答不胡答
- 实测：最终 Top-3 = VPN-001（VPN认证失败）、MAIL-003、VPN-003，耗时 ~500ms，未触发拒答

### 阶段 F：Small-to-Big 回溯（`expand_to_parents` [parent_child.py:188](../rag_pipeline/chunking/parent_child.py) + `rag_service/mapping.py:66`）

- 做什么：把最终命中的子块展开成父块全文——读 metadata 里的 `parent_content` 字符串 + 按 parent_id 去重，**零 IO、零二次检索**
- 服务出口 `mapping.py` 强制 `content` 优先取 `parent_content`，即使精排粒度是 child 下游也不会拿到半截卡
- 实测：结果 1 的命中片段只是 c0 的 253 字符"现象描述"，返回给 LLM 的是 820 字符整卡——现象、根因、员工步骤、工程师步骤全链路完整

## 四、metadata 与存储位置

| 存储位置 | 内容 | 用途 |
|---|---|---|
| `chroma.sqlite3`（`embeddings_queue` 表） | 向量 4096 维 float + 原文 + **metadata JSON**（含 parent_content） | Dense 检索 + 回溯 |
| 同库 `embedding_metadata` 表 | metadata 拆成键值行 | `filter={"wiki_status":"现行"}` 硬过滤 |
| BM25 语料（内存，不落盘） | 启动时从 wiki/*.md 现场重切（与索引共用 `build_chunker` 工厂+同配置，保证 chunk_id/边界一致） | 关键词召回 |
| `manifest.json` | wiki_fingerprint + config_fingerprint | 配置/语料变更自动判旧库失效 |

**为什么每个子块都内嵌 parent_content（而不是像 LangChain 官方 ParentDocumentRetriever 存独立 Docstore 按 id 查）**：
1. 事先不知道命中哪个子块，任一子块都必须能独立回溯；
2. BM25 通道在内存、不经过向量库，父块必须跟子块走；
3. 回溯发生在 RRF 后/精排前/装配出口多个点位，内联=零查询，Docstore=每处一次 IO。

代价是子块数 × 父块大小的存储冗余——当前百卡量级仅 MB 级，可忽略；语料上万卡时再切换 Docstore 方案，且只需改 `expand_to_parents` 一个函数（全链路唯一展开入口）。
