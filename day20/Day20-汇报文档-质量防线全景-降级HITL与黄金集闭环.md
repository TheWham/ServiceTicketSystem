# 第一部分 · 优雅降级防线（3 分钟）

## 1.1 交付红线（Day19 讲义第三篇 · 工业级 Fallback 三标准）

1. **阻断破坏，兜住底线**：任何未捕获错误不得穿透到外部用户
2. **具身化业务引导**：告知用户"网络不可用"还是"参数不合法"，而非生硬技术报错码
3. **沉淀 Bad Case 到待修复流水**：报错入参自动记录，供黄金问题集回归扩充

## 1.2 标准 1+2 的落地：四层隔离壳（真实项目代码）

`GuardedRagClient`——RAG 依赖的隔离壳，**四层防御顺序固定，逐层短路**：

```
请求 → ①断路器(连续5败打开/30s半开/3成关;打开期间不发请求直接降级)
     → ②并发上限(Semaphore 非阻塞获取,拿不到立即降级;独立线程池与 Web 主线程隔离)
     → ③超时预算(一次请求一份预算,各环节从 remainingMillis 扣减;超时 cancel(true) 中断)
     → ④有界重试(最多 1 次,只重试 TIMEOUT/UNAVAILABLE;业务性拒绝绝不重试)
```

**三出口承诺：本类永不抛异常。**
出口 A 成功返回 / 出口 B 循环走完带降级结果返回 / 出口 C `catch (Throwable)` 收敛——异常细节只进服务端日志、不进响应（AI-006）。**标准 1 完成闭环。**

**标准 2 的落地：7 类结构化拒答（AiRefusalReason）**
`NO_RELIABLE_KNOWLEDGE / LOW_CONFIDENCE / CONFLICTING_KNOWLEDGE / HIGH_RISK_TOPIC / MODEL_UNAVAILABLE / POLICY_BLOCKED / OFF_TOPIC`，每类路由到具身化话术（如 HIGH_RISK →"该请求涉及高风险操作，请转人工处理"）。模型故障**不抛 AI_UNAVAILABLE**，而是降级为结构化拒答 + suggestTransfer——会话保活、对话记录完整（RD-006/RD-013）。

## 1.3 检索不出来时的兜底决策链

```
检索零命中/低分
  ├─ 有工具意图(查工单/建单) → 工具兜底: agent 凭真实工具实据回答
  │    (generalAnswer=true,正文带"无知识库依据"标注,引用守卫拦截冒充)
  ├─ 无工具意图 → 确定性拒答(宁可拒答,不幻觉):
  │     REFUSE + refusalReason + suggestTransfer=true
  │     "暂时无法给出可靠的 IT 建议，请转人工或直接提交工单"
  └─ 拒答记录 → 落库 → bad case 流水线(见第二部分) → 补知识/进黄金集
```

**为什么不让模型自由发挥兜底**：企业 IT 场景答错的成本远大于说不知道的成本。模型通用能力通道**存在且已放宽**（generalAnswer=true 的 ANSWER 允许无引用），但必须如实打标、且 `usedVersionIds ⊆ 预检索材料` 的伪造守卫拦着——想"假装查到了"整次作废。**兜底不是把问题藏起来，是先给建议、再给出口（转人工/工单草稿）、最后把缺口变成资产。**

## 1.4 现场演示 ①：拔线降级（90 秒）

**HITL 双门禁演示脚本 `day18/hitl_demo.py` 预跑环境后**：

1. 停掉 agent_service（:8320）→ 再发一条消息
2. 系统表现：`GuardedRagClient` 重试 2 次 → 返回结构化拒答 `MODEL_UNAVAILABLE + suggestTransfer=true`，**服务零崩溃、零堆栈泄露**
3. 开终端实时看降级 WARN 滚动（`tail -f logs/consultation.log | grep 降级`）
4. 恢复 agent_service → 系统自动回正常，无需重启

> 话术："拔掉依赖，用户拿到的是结构化拒答而不是 500——这就是标准 1、2 的现场自证。"

# 第二部分 · HITL 人机回环闭环（1.5 分钟）

## 2.1 原理：读写分离门禁 + Suspend → Sign → Resume

课程主线（day18 三位一体 Agent）：
- **读写分离门禁**：合规单 → `AUTO_PASS` 全自动放行；高风险追回 → `REQUIRE_HUMAN_APPROVAL` **物理挂起**
- **签名令牌**：HMAC-SHA256 签名 + TTL 有效期 + `consumed_tokens` **防重放** + 挂起上下文快照
- **恢复接口**：验签 → 驳回分支（不落库）→ 授权分支（恢复状态机 → 下发 OA 工单）

## 2.2 真实项目落地点睛：双门禁同构

"自动化不是发现就干，而是**发现 → 挂起 → 人点头 → 才干**"，在真实 it-ticket-cloud 微服务里落了两处：

| 门禁 | 流程 | 现场看点 |
|---|---|---|
| **① 派单** | 自动路由算好"派给谁"写入草案 → 工单**停在 NEW 一步未动** → 工程师接单被 409 拦 → 主管放行才 ASSIGNED | 流转日志 operator 是人不是系统 |
| **② AI 建单** | AI 只产**草稿** → 提问"库里多了单吗？"→ **没变** → 员工确认才真建，且新单又落回门禁① | "建单要人确认，派单还要人确认"连环叙事 |

## 2.3 现场演示 ②：双门禁闭环（1 分钟）

```bash
python day18/hitl_demo.py        # 可反复重跑(幂等键已带时间戳)
```

**防重放攻击演示**（与质量侧联动）：伪造 Token 调恢复接口 → 验签拦截（签名+TTL+防重放）→ 100% 拦截零崩溃。

> 话术备注（如被追问）：演示中"派单草案端点未经网关路由、需直连 + X-User-Id 头"是已知缺口，如实说明并给补救方案（补一条网关路由）——诚实交代缺口比被评审发现更可信。

# 第三部分 · 黄金数据集运营闭环（3 分钟，核心产出）

## 3.1 问题与背景

拒答数据已按 AI-008 规范落库（`consultation_message.citation_json` 含结构化 `refusalReason`），黄金集 `golden_dataset_v1.1.json`（37 条）已定盘——**但"记录"和"运营"之间断了一环**：知识库管理员看不见拒答、够不着黄金集，只有运维脚本能导出。同样的知识缺口反复出现，没有积累。

## 3.2 方案：三层流水线在线化

```
员工提问 → AI 拒答(REFUSE) ──落库(已有,零改动)──┐
                                              ▼
【页面① 拒答处置】 实时联查 REFUSE 消息 → 知识管理员三选一：
    ├─ GOLDEN_QA      补知识 → 进黄金集正常区(回归验证"答得对")
    ├─ GOLDEN_REFUSAL  越界题 → 进黄金集对抗区(回归验证"仍拒答")
    └─ DISCARD        噪音/基础设施故障 → 不进评测
                                              │
【页面② 黄金数据集】 实时条目列表 + 统计大盘 ◄──┘
                                              │
                    golden_export.py 导出 ──→ evals/golden_dataset_v2.0.json
                                              │
                    现有 6:2:2 评测管道跑分（零改动）→ 回归报告
```

**一句话卖点**：从员工问出一个问题，到它变成黄金集里的回归考题，全程 **2 分钟、4 步、零代码改动**。

## 3.3 关键设计决策（每条有代码出处）

| # | 决策 | 理由 |
|---|---|---|
| 1 | **待处置列表 = 实时联查，不建同步队列** | 拒答数据天然落库，`LEFT JOIN bad_case_review` 即区分待处置/已处置——零同步延迟、零一致性风险、不侵入主流程 |
| 2 | **人工闸口保留，拒绝"拒答即坏例"全自动** | 区分**知识缺口**（本该答对→补知识→正常区）与**设计性拒答**（越界题→对抗区验证"仍拒答"）。把正确拒答当缺陷修=制造幻觉 |
| 3 | **golden_case 表为评测集唯一真源** | 页面读表；评测管道继续读 JSON（硬取 id/query、其余容错），导出脚本从表出 v2.0——**评测代码零改动** |
| 4 | **处置事务原子** | 同一事务写处置+入集；`UNIQUE(ai_message_id)` 一条拒答只处置一次，重复返回 409 |
| 5 | **软删不物理删** | 与"已发布知识不物理删除"（PRD §16.4）同一原则，回放可追溯 |
| 6 | **权限收口** | 端点守卫 KNOWLEDGE_ADMIN / PLATFORM_ADMIN，EMPLOYEE 实测 403 |

**拒答置信度 0.00 的精确语义**（预埋应答）：
- OFF_TOPIC / HIGH_RISK = 0：意图分类在检索**之前**拦截，无评分语义
- LOW_CONFIDENCE = 0：**检索零命中**——知识缺口的强信号
- Java 层已实现真实分数透传（`RagResult.refuse` 重载 + 五处 `topScore` 透传），检索契约放宽后处置页立即显示真实分

## 3.4 实现清单（30 秒带过）

- **数据层**（V2_6 纯增量）：`bad_case_review` 处置决策表 + `golden_case` 评测唯一真源
- **后端**：consultation-service `RefusalCase*` 三件套（实时联查+处置事务）；rag-service `GoldenCase*`（分页/统计/增改/软删）
- **前端**：`/knowledge-admin/refusals` 拒答处置 + `/knowledge-admin/golden` 黄金数据集
- **脚本**：`golden_seed_import.py`（37 条幂等种子）、`golden_export.py`（表 → v2.0.json，评测零改动）

## 3.5 实测数据（2026-10-23 真实环境）

| 验证项 | 结果 |
|---|---|
| 待处置拒答池 | **376 条**（线上真实流量实时联查） |
| 黄金集规模 | **38 条**（37 SEED + 1 BAD_CASE 沉淀），对抗 22 / bad case 沉淀 1 |
| 处置闭环 | 年金折现越界题 → GOLDEN_REFUSAL → goldenCaseId=38 → 页面立即可见 ✅ |
| 防重 | 重复处置 → **409** ✅ |
| 越权 | EMPLOYEE → **403** ✅ |
| 导出-评测兼容 | v2.0（38 条）→ 现有 `golden_evaluation.py` 零改动可跑 ✅ |

**6:2:2 配比诚实披露**：

```
标准:  基础业务题 60% / 版本冲突题 20% / 越界拒答题 20%
实际:  基础业务题 32% / 版本冲突题 11% / 越界拒答题 58%
```

解读：冷启动期拒答沉淀快是正常现象；配比失衡是"该补知识了"的运营信号——随 GOLDEN_QA 补知识运转，正常题占比回升。**配比评审已列入处置页运营看板职责。**

## 3.6 现场演示 ③：闭环 2 分钟（核心演示）

1. **制造**（可选）：员工在智能客服问知识库外问题 → 结构化拒答
2. **查看**：知识管理员登录 → "拒答处置" → 该条在待处置列表（问题/原因/零命中置信度）
3. **处置**：点"处置" → "进黄金集·对抗区" → 提交成功
4. **沉淀**：切"黄金数据集" → 统计 +1、来源标记 `bad case`、类型标记 `对抗`
5. **回归**（切屏）：`golden_export.py` 导出 v2.0 → 评测管道跑分 → 数字同步

> 收尾话术："三条 Fallback 标准里，标准 1、2 由四层隔离壳和结构化拒答兜死；标准 3 由这条流水线变成每天自转的闭环——**AI 系统的可靠性不再是修出来的，是运营出来的**。"

# 第五部分 · 与真实生产项目的同构声明（升华点）

本模块的设计哲学与生产级实现一一对应：

| 课程/本项目实现 | 生产项目（it-ticket-cloud）同构物 |
|---|---|
| 读写分离门禁 + Suspend→Sign→Resume | 派单草案门禁 + AI 建单草稿确认（状态机 + 流转审计） |
| 签名令牌防重放 | HMAC Token + TTL + consumed_tokens |
| 四层隔离壳 + 三出口 | `GuardedRagClient` + `SimpleCircuitBreaker`（断路器 5败开/30s半开） |
| 结构化拒答 7 类 + suggestTransfer | `AiRefusalReason` 枚举 + RD-006 失败语义 |
| 拒答 → 落库 → 处置流水 | `ai_interaction` 审计 + 员工反馈知识优化队列 |
| 黄金集唯一真源 + 软删 | 知识版本化生命周期（不物理删除） |

> **收束**：写操作要人点头（HITL 门禁），学知识也要人点头（人工标定闸口）——同一个原则贯穿 AI 交付的每条写路径。三条 Fallback 标准：防线兜死下限，门禁守住写路径，流水线让系统**越用越强、可靠性单调递增**——这是传统软件 QA 和 AI 交付最大的区别。
